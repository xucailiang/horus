## 1. 概要

建设独立项目 horus：一个完全业务无关、面向 Agent 的 AI 原生后端接口测试平台，必须同时提供 MCP Server、CLI 和 Skill。用户提供 API 文档、补充说明、请求示例、可选的宿主源码分析或聊天补充资料、测试环境和凭据，由 Codex/Claude 等外部 Agent 中的 LLM 分析接口语义与实现，建立业务流程、业务规则、接口关系和数据依赖，设计测试链路、测试数据、提取与记录策略。业务理解必须成为正式测试计划的一部分，供人工审核。只有审核通过的计划版本才能进入正式执行，得到有证据支持的报告；CI 重跑已审核版本。

通用性验收原则：切换业务或后端语言，只替换接口资料、环境和计划；Rust、Go、TypeScript、Python 等 HTTP 服务无需平台语言适配，源码不是执行前提。

主要使用场景：用户在 Codex、Claude Code 等 Agent 工具中连接 horus MCP，由宿主 LLM 理解和规划，horus 执行并返回证据与报告。首次安装配置完成后，创建项目、接入资料、配置草案、审核、执行、等待和报告均须经 MCP 完成；CLI 用于安装诊断、辅助操作和 CI。主链路契约和真实双客户端验收见 [Agent + MCP 使用链路](AGENT-MCP-WORKFLOW.md)。

用户体验的验收主线：提供部署地址、资料、凭据与测试边界 → 自动分析业务并生成计划 → 审核确认具体版本 → 自动准备、执行、校验、清理并生成报告。用户无需手写请求、链路、捕获规则和断言，批准后无需逐步推动任务。

首版“任意后端”指不同业务领域、满足 HTTP/REST + JSON 接入能力且提供充分资料和访问条件的已部署服务。特殊签名、外部验证码或不可自动准备的依赖须在执行前集中说明，不能通过默认成功掩盖能力缺口。报告只对实际测试覆盖给出结论。

## 3. 背景与边界

用户需要从被测系统的资料出发，自动形成测试计划并执行。现有候选在完整 AI 能力开放程度、业务理解、执行流程或自部署能力上未能直接满足需求，因此采用独立项目路线。

AI 原生应落实到接口理解、依赖识别、数据设计、计划生成和执行反馈分析，这些推理工作由外部 Agent 中的 LLM 承担。平台以稳定、结构化、可查询、可组合的工具提供上下文和执行能力。HTTP 请求发送、结构校验、断言计算、任务调度和证据保存由确定性程序承担。

### Agent 与平台的职责边界

| 参与者 | 职责 |
| --- | --- |
| 用户 | 提供目标、资料、环境、凭据和测试边界；集中审核业务理解、计划、写操作、清理与负载预算，无需手写逐接口配置或推进执行步骤 |
| Codex/Claude 等 Agent | 理解资料与源码，选择只读探测，推断依赖与规则，生成或修改计划，分析结果和提出补充测试 |
| 平台 MCP 工具 | 返回资料与源码上下文，执行受限探测，保存和校验计划，输出审核材料，检查审核状态后执行，记录与查询证据 |
| 平台 CLI | 安装诊断、辅助操作及 CI 回放，共用核心；不是日常 Agent 流程的必经步骤 |
| Skill | 指导 Agent 自动接入、分析业务、形成计划、展示并记录用户明确确认、等待运行完成和呈现报告；不能自行代替用户作出批准决定 |
| CI | 检查已有计划及审核记录，在配置好的环境中执行，并按结果策略决定任务状态 |

平台保存的计划应完整到足以独立执行，运行时不需要靠原始聊天记录补齐参数、变量来源或预期。依赖临场 LLM 判断的检查须单独标注，在无 Agent 的 CI 中不得自动计为通过。

平台面向不同业务系统学习各自的业务语义。识别出的业务知识属于具体被测项目的版本化资产，不进入平台的硬编码逻辑。

当前工程采用 Python 3.12 + uv、共享核心、FastMCP Server、CLI、通用 Skill、文件存储、Hurl 功能执行适配器及 k6 压测适配器；核心流程已实现，模型由调用方 Agent 管理。历史选型和闭环调整记录在 ADR-0002/0003。

## 4. 目标与验收原则

### 4.1 产品目标

1. 用户无需逐条手写接口请求、链路和断言，即可得到可检查、可修改、可执行的测试计划。
2. 测试计划先说明 LLM 对业务流程与规则的理解，再说明测什么、为何测、如何准备数据、如何关联接口、记录什么、如何判定，供人工整体审核。
3. 每次执行都有真实请求与响应证据，可定位失败步骤并说明前置条件。
4. Agent 发现新问题后可增补测试，所有新增动作归属明确的新版本，并在人工审核后执行。
5. 同一套平台可用于不同业务系统，避免为每个项目修改测试平台代码。
6. 覆盖常规接口测试检查，并提供可配置负载下的请求数、吞吐量、响应延迟分位数、HTTP 错误率、数据断言失败率及阈值判定。
7. 接入时集中说明必要输入、能力缺口及阻塞；审核后自动完成已批准任务并输出报告，不因可选补测继续打断用户。

### 4.2 候选验收场景

- 使用同一套平台代码接入两个不同业务领域的后端，仅修改资料、环境和配置。
- 接口清单、链路、数据方案、捕获规则、断言及操作范围建议由 Agent 自动生成；用户只提供必要资料与边界并审核，不手写测试脚本。
- 在当前 Agent 对话确认展示过的具体版本即可开始执行，不要求再运行一次 CLI 批准；模糊或旧版本确认不能复用。
- Codex 与 Claude Code 分别在真实客户端中，从空 horus 工作区经 MCP 完成建项目、资料/配置接入、规划、审核、执行和报告；不以通用 MCP 客户端模拟替代真实宿主验收。
- 重试同一次启动请求不重复执行；等待超时不重新启动，断开重连后可按项目/运行引用恢复查询。多会话不能串用项目或批准。
- 单轮执行在正常、失败、部分阻塞或超时下均自动收尾，报告说明执行覆盖、失败证据、清理结果及待处理项。
- 人工能从计划读懂推断的业务流程、规则、状态、数据依赖、依据与未知项，并追溯到对应测试用例和断言。
- 未审核或审核不匹配的版本在 MCP、CLI、CI 中均不能正式执行；AI 不能通过计划字段自行声明审核通过。
- 对包含认证、创建、查询、修改、删除的接口集合，自动生成合理链路，并从前一步响应提取后续需要的动态值。
- 对包含状态限制、异步结果和不同身份的后端，自动生成状态/权限测试、条件分支及有界轮询；能检出非法状态变化和未授权访问。
- 对文档缺失或互相矛盾的信息保留未知项，报告解释其对测试的影响。
- 在计划产生前，只读探测不会创建、修改或删除业务资源。
- 给定明确预期，能够检出预先设置的错误，例如返回结构不符、非法输入被接受、权限约定被违反或已声明的数据一致性规则被破坏。
- 步骤失败后，依赖该步骤的测试标为阻塞或未执行，并保留原因，不计入已通过。
- AI 增补测试时，原始计划和历史结果仍可查看，补充步骤可追溯到触发它们的证据。
- 在相同服务版本及可恢复的前置条件下，可重放已保存计划；每次运行的变量和数据相互隔离。
- 保存计划后，关闭 Agent 仍可通过 CLI/CI 执行其中可确定性判定的检查，得到结构化结果与报告。
- 首个交付包含基础并发压测，实际采集并发配置、完成请求数、吞吐量、平均延迟、P50/P95/P99、HTTP 错误率和数据检查失败率。
- 在响应状态仍为 200、数据违反明确约定的情况下，功能测试与压测数据检查均能失败，不能仅根据 HTTP 成功判定通过。
- 性能阈值未配置或样本不足时明确提示；不得自动得出性能达标结论。

实际业务系统的质量阈值、规模、运行耗时和模型成本目标由接入配置确定。技术方案中的测试后端负载和阈值仅用于工程验收，不代表通用业务 SLO。

## 5. 使用对象与场景

首要任务是帮助开发者和测试人员验证后端接口的契约、业务链路与数据一致性。

典型场景包括首次接入一个后端、接口变更后的回归、针对指定模块补充测试，以及分析失败并生成有针对性的后续测试。

首版主要服务在 Codex / Claude Code 中连接 MCP 的开发者和测试人员，CI 另经 CLI 执行已审核计划。协议范围为 HTTP/REST，主要处理 JSON 请求与响应。多人、组织权限及对外服务能力尚未确认。

## 6. 用户价值与核心交付物

一次完整测试任务应留下以下关联资产：

| 资产 | 内容 |
| --- | --- |
| 输入资料快照 | 文档版本、源码仓库与 commit、环境标识；不保存明文凭据 |
| 系统理解结果 | 接口语义、实体与状态、依赖关系、约束、依据与未知项；写入计划的业务理解部分，不能仅留在聊天或知识库 |
| 测试计划 | 业务理解、覆盖映射、范围、链路、数据方案、提取和记录策略、断言、清理、执行策略 |
| 审核记录 | 计划版本、审核人、决定、时间、意见、环境及允许的操作与负载范围 |
| 执行记录 | 计划版本、审核记录、每一步实际请求与响应、提取变量、断言结果、错误与耗时 |
| 测试报告 | 执行结论、覆盖范围、失败证据、阻塞与不确定项、复现方法、后续建议 |
| 计划演进历史 | 补充测试的原因、差异、关联运行与新增结果 |

## 7. 功能需求

### 7.1 端到端流程

Agent 模式：提供资料、环境、凭据与边界 → 自动接入和源码定位 → 必要时只读探测 → 分析业务与生成测试设计 → 内存校验并直接在对话展示计划及缺口 → 人工确认 → 保存同一计划 → 平台自动准备、执行、采集、校验和清理 → 自动生成报告 → Agent 呈现报告并解释结果。补充测试作为独立新版本送审，不阻塞本轮报告。

CI 模式：读取已有计划、审核记录与项目配置 → 检查版本、审核范围和可执行性 → 执行与采集证据 → 生成报告与退出状态。缺少有效审核时阻塞，不能静默改为自动批准。发现计划之外的行为时，保存异常供后续 Agent 分析；CI 不自行扩展计划。

只读探测是计划阶段的受限活动，不与正式测试执行混记。文档和源码已足够时，不要求进行无意义的探测。

### 7.1.1 Agent / MCP 主链路与 CLI 使用体验

- CLI 与 MCP 访问一致的项目、资料、计划、执行和报告能力，结果可以互相引用。
- 提供面向人的摘要和面向 Agent/CI 的结构化结果；具体命令和工具名称在技术设计时确定。
- 调用者可提交任务目标、资料位置、源码仓库、环境和项目执行策略。
- 较长任务可以获取运行标识并查询状态、进度、结果和失败证据，避免依赖一段无法追踪的终端输出。
- CLI 退出状态和 MCP 返回结果应清楚表达测试结果、阻塞和平台执行错误，具体映射在接口设计时确定。
- CI 对结果的失败门槛可配置，不把待判定项静默计为通过。
- 首版以宿主 Agent + MCP 为主要交互入口；Web 控制台不属于首版，CLI 不作为补齐 MCP 缺失能力的隐藏前置步骤。
- MCP 工具输出应提供后续可用的资料、计划、运行和证据标识，Agent 可分步取用，避免单次返回全部源码或执行日志。
- Agent 的系统理解与结论需保存到项目资产，后续会话可检索恢复，不能只留在聊天上下文里。
- Skill 自动编排接入、内存校验、对话展示、确认后保存、启动、等待与呈现报告。测试计划直接回复在聊天中，不塞入 Ask 卡片；确认前不保存计划或创建测试版本目录。
- 每次执行作为一轮版本测试，计划和报告同放一个独立目录，包含可读计划、可执行快照和 Markdown 报告；新一轮不覆盖上一轮。
- 测试计划和报告均为 Markdown，语言跟随当前 Codex/Claude Code 对话，计划保留完整 Mermaid 调用图，报告使用对应的业务简图。报告先展示结论、问题和关键数据，每组业务结果占一行。逐步断言与请求响应放在同目录的 details.md，主报告通过链接引用，不重复嵌入完整执行记录。
- 随产品提供工作流 Skill，说明理解、探测、计划、人工审核、执行、诊断、增补和报告的流程。审核状态、权限、负载和写操作范围由核心程序校验，Skill 不承担强制约束。
- CI 通过 CLI 调用共享核心执行已有且审核有效的版本，功能执行使用 Hurl，压测使用 k6；无需安装 MCP 可选依赖、启动 MCP 或调用 LLM。
- MCP 提供能力检查、列出/创建/恢复项目、保存配置草案的入口。草案不会自动扩权，配置快照与计划合并为一次具体版本审核；执行仍受服务端和用户既定上限限制。
- MCP 使用 projectRef 等稳定引用显式隔离项目，避免不同聊天共享一个可变“当前项目”；恢复会话可取回资料、计划、审核与运行摘要。
- 测试启动具备请求幂等性，资料抓取和运行采用快速返回引用及状态的方式；错误返回原因、下一步及是否需要用户补充。
- 报告和审核材料可经 MCP 读取，不能仅返回宿主无法访问的服务端路径。上下文、事件和报告分页返回。
- 安装说明分别覆盖两客户端的 MCP 配置、Python 3.12/uv 路径与环境、凭据传递和 Skill 发现。宿主权限授权与 horus 业务审核分别说明，不自动关闭客户端权限检查。

### 7.2 资料接入与项目配置

- 接入 API 文档、补充说明、请求示例与业务规则。
- 解析 OpenAPI/Swagger 定义链接及常见 Swagger UI 链接。源码由 Codex/Claude Code 按需读取；聊天资料和源码结论直接随计划保存，不建设专用 Git、源码检索或知识渠道。
- 配置测试环境、服务基础地址、可访问范围与鉴权。模型由调用方 Agent 配置和管理。
- 接口定义保存固定内容，审核绑定具体计划；可选上下文保存在计划内，避免额外的资料版本体系。
- 源码用于定位路由、请求与响应结构、校验规则、认证与权限、状态变更及关联数据逻辑。
- 源码分析范围应按任务需要展开，不要求一次性把整个仓库交给模型。
- Agent 从资料生成操作目录、鉴权/身份绑定建议和项目范围草案，受用户预设边界约束并随计划集中审核，不能自行扩大执行权限。
- 地址不可达、凭据缺少、特殊鉴权不支持或外部依赖无法准备时，在执行前集中列出；资料不足保留未知，不要求用户先手写完整测试配置。

### 7.3 系统理解与依据管理

外部 Agent 中的 LLM 应结合平台提供的上下文识别：

- 各接口的目的、输入、输出、错误行为和使用条件。
- 认证方式与权限条件。
- 资源之间的关联及创建、读取、更新、删除等生命周期。
- 字段校验、状态迁移和具有明确依据的跨接口一致性规则。
- 响应字段如何作为后续路径、查询、请求体或鉴权参数使用。
- 哪些结论有明确资料支持，哪些来自源码推断或探测，哪些仍未知。

每条影响测试的规则应记录来源，例如文档位置、源码文件与符号、commit 或探测记录。预期结果以明确需求和接口约定优先，源码用于辅助推断与定位，实际响应用于观察和验证。文档、源码与响应冲突时保留各方证据，并单列冲突和不确定项。

源码和真实响应都是被测对象的事实材料，不能因为实现当前这样返回，就自动认定该行为符合需求。

业务理解以可读摘要和结构化对象同时保存到正式计划，至少包含参与者/资源、业务流程及触发条件、状态变化、规则和不变量、接口与数据依赖。每项有稳定 ID 与依据；流程关联 case，规则关联 assertion，字段依赖关联 capture。没有测试覆盖的理解项标明未覆盖及原因。

平台只定义这些通用结构，不预置某个行业的实体或业务模板。LLM 根据当前项目文档和源码填充内容；人工审核确认的是该版本的理解与测试设计，不代表自动消除了所有材料冲突。推断、冲突和未知项保持显式状态。

### 7.4 正式计划前的只读探测

以下保留原设计约束。当前没有独立的计划前探测执行入口，probeAllow 为保留字段；现有流程依据资料规划，业务请求在计划批准后执行。

- 在已配置的测试环境与接口范围内执行。
- 每个探测动作记录目的、预期读取内容及实际请求与响应。
- 不仅按 HTTP 方法判断只读性，还结合文档、源码和配置判断动作是否可能修改状态。
- 无法确认只读性的动作不在计划前执行。
- 需要通过写操作准备资源时，将该动作放入正式测试计划，等待校验与人工审核。
- 探测优先使用用户提供的有效凭据；有状态的登录、会话初始化等流程归入正式计划，除非后续明确允许作为探测前置步骤。
- 探测失败或材料不足时，可保留未验证假设，并说明哪些计划步骤因此不具备执行条件。

### 7.5 测试链路设计

- 构建接口与步骤之间的依赖关系，区分顺序、可并行、条件分支和必要等待。
- 区分数据准备、被测操作、验证和清理步骤。
- 支持动态资源标识、会话与 token 在步骤间传递。
- 对失败后的继续、阻塞、重试和清理行为作出明确规定。
- 等待、轮询、重试设置可解释的上限；不会通过无限重试掩盖失败。
- 正常流程、边界输入、异常输入、权限和状态变化的覆盖应说明选择依据。
- 首个交付明确提供声明式条件分支、有界只读轮询、显式身份/凭据切换及状态/跨步骤关系断言；分支和等待的最坏请求量计入审核预算。
- 身份、轮询条件和失败后的行为预先写入计划；正式执行不能依靠 LLM 临场补齐动作。

### 7.6 测试数据设计

- 为每个用例说明数据来源：资料示例、已存在测试数据、运行中读取或新建、按约束生成。
- 区分有效值、边界值和明确用于验证异常处理的无效值。
- 避免编造需要真实存在的资源 ID 或外部依赖数据。
- 为数据建立步骤间关联、运行隔离、生命周期及清理方案。
- 不能自动准备的数据明确列为前置条件或阻塞项。
- 记录新建资源及清理结果，清理失败保留待处理清单。

### 7.7 数据提取、记录与记忆

“记录数据”包含四类用途：

| 用途 | 例子 | 要求 |
| --- | --- | --- |
| 链路运行变量 | token、资源 ID、版本号、游标 | AI 设计提取规则、用途、作用域和失效条件 |
| 断言与比较数据 | 创建前后的字段、列表与详情的一致性 | 在计划中声明比较关系和预期依据 |
| 执行证据 | 请求、响应、错误、耗时、实际断言值 | 由平台保证最小证据完整性，不由 AI 任意省略 |
| 项目知识 | 已验证的关联、约束与未知项 | 关联资料版本和证据，区分确认事实与推断 |

每条提取与记录规则至少说明：来源步骤、字段或表达式、用途、作用域、保留策略和敏感性。

敏感凭据以引用方式保存，报告和模型上下文按配置脱敏。不同项目、环境和运行的变量不可意外串用。

响应截断或脱敏影响到可判断性时，在报告中说明；保留足够证据定位相关断言。

### 7.8 正式测试计划

计划必须是可读、可编辑、可校验、可版本化的结构化资产。首版格式在技术设计时确定。

计划至少包含：

1. 目标、测试范围、输入资料版本、源码版本及环境。
2. 业务理解：业务流程、参与者/资源、状态变化、规则与不变量、接口与数据依赖、依据、推断、冲突和未知项。
3. 业务流程到用例、业务规则到断言、数据依赖到捕获和参数的覆盖映射，以及未覆盖项及原因。
4. 前置条件、鉴权、已有数据和外部依赖。
5. 场景与用例，以及每个场景的目的和预期。
6. 步骤顺序、依赖、分支、参数和执行动作。
7. 测试数据来源与生成规则。
8. 变量提取、字段记录、证据和保留策略。
9. 检查项、预期值或关系、依据和不确定性。
10. 超时、重试、等待、失败处理和清理策略。
11. 预计动作规模、写操作清单、并发与负载阈值、已知阻塞项。

生成后进行结构和可执行性检查，包括变量是否有来源、依赖是否可满足、断言是否有依据、所需动作是否符合项目配置。

计划生成并通过校验后进入待审核状态，导出包含业务理解、测试设计、写操作与清理、负载预算、冲突未知项及版本差异的审核材料。人工可以批准、拒绝或提出修改意见；修改产生新版本，不覆盖已审核内容。

人工批准绑定具体不可变计划版本及环境、操作与负载范围。审核通过后，该版本可在有效范围内自动执行并由 CI 重跑，无需逐个 HTTP 请求确认。首次计划、新增用例、修改断言/参数/业务理解或 AI 补充测试产生的新版本，均须重新审核。超出项目配置或审核范围的动作阻塞并说明原因。

支持两种等效入口：在 Codex/Claude 展示计划后，用户明确确认，由 Agent 记录该具体版本和范围的人工决定；或由用户在 CLI 审核。前者不要求重复运行 CLI。Agent 可以记录已经发生的人工决定，不能自行作出决定或把一般测试意图当成对未知版本的批准。

CI 从受信任的版本库或产物读取审核记录，不自行产生批准。记录人工决定的本地工具不等于具备强身份认证，具体信任边界和版本检查由技术方案明确。

### 7.9 测试执行与计划演进

- 执行器按照具体且审核有效的计划版本执行动作，并记录审核引用及真实证据。
- 新增、修改、删除等写操作按项目配置执行，记录产生的资源及清理结果。AI 补充计划也必须遵守同一范围，不能自行扩大权限。
- 每个步骤具有明确状态，至少能够区分通过、失败、阻塞、跳过、执行异常和待判定。
- 区分被测系统不符合预期、生成用例无效、环境问题和平台执行错误。
- Agent 可根据反馈解释失败并提出补充测试。
- 新增或改变测试动作前，生成新版本计划，保存变更原因、差异及触发证据；校验和人工审核后再执行新增动作。
- 新版关联已有执行记录；复用结果时检查环境、数据和前置条件是否仍有效。
- 发现异常不自动修改原有预期使其通过；修改预期需有可追溯的新依据。
- 平台为执行步数、轮次、并发和请求规模设置上限；模型调用与 token 预算由调用方 Agent 管理。
- CI 执行模式不自动开展需要 Agent 的计划扩展；相关发现留作后续任务。
- 首个交付支持运行状态查询、取消、整轮重跑和失败后的清理修复入口；暂停后恢复任意中间步骤不在首个交付范围内。
- 单轮有总体时限、轮询上限及独立清理预算，发生失败、阻塞、引擎异常或取消仍进入收尾和报告；强杀后的中断在下次查询时恢复摘要与账本，不宣称断电期间仍能生成报告。
- 新版待审核不阻塞本轮结束，不把连续补测当作无限延长的同一次运行。

### 7.9.1 常规检查与并发性能测试

| 类别 | 应提供的检查或指标 |
| --- | --- |
| 基础响应 | 状态码、响应头、必要字段、类型、JSON 结构、响应耗时 |
| 数据断言 | 字段值、存在性、长度/数量、范围、格式及具有明确依据的字段关系 |
| 流程 | 鉴权、动态数据传递、前置条件、资源生命周期、失败阻塞与清理 |
| 异常与权限 | 缺少必填项、无效/边界值、错误 token、缺少权限、资源不存在 |
| 功能并行 | 独立链路的有界并行；链路内部按依赖顺序执行 |
| 基础压测 | 虚拟用户数、配置/完成迭代数、完成请求数、实际吞吐量、平均及 P50/P95/P99 延迟、HTTP 错误率、数据检查失败率、阈值结果 |

首个交付的压测使用固定并发数和固定总请求数，对预先创建的隔离资源执行读取并发。负载开始前由计划完成鉴权及资源准备，结束后由平台清理，避免把准备/清理耗时混进接口延迟指标。

用户可配置各环境的并发上限、请求规模、超时及阈值。源码只能辅助识别检查点，不能证明某个后端的性能 SLO。阶梯加压、长时间稳定性、容量极限和并发写入竞争测试属于后续扩展，不归入首个交付的“基础压测”。

### 7.10 断言与结果判定

- 标准化的状态码、结构、字段约束与关系校验尽量由程序计算。
- 语义性检查可由 Agent 中的 LLM 辅助，结论必须关联输入和证据。需要 LLM 的检查在纯 CLI/CI 模式中标明待判定，或在计划生成时转化为有依据的可执行断言。
- 事实观测、预期依据、AI 推断和最终判定分别保存。
- 缺少可靠预期或依赖不满足时明确标记，不把“收到响应”当成业务正确。
- 报告中的确定性失败与可能存在的问题分别呈现。

### 7.11 测试报告

报告至少包含：

- 本次测试目标、计划版本、审核记录、环境、资料与源码版本、运行时间。
- 计划中的业务理解、流程/规则与用例/断言的对应关系，以及推断、冲突和未覆盖项。
- 接口与场景的计划覆盖、实际执行覆盖、未执行范围及原因。
- 各类结果统计，以及每条链路和用例的执行详情。
- 失败步骤、预期与实际、依据、相关请求响应及上下游数据。
- 可恢复前置条件、数据准备方法和复现步骤。
- 阻塞、环境异常、清理失败、材料冲突和待判定项。
- AI 根因假设及其证据，与已确认事实清楚区分。
- 补充计划及其执行结果、后续建议。
- 请求数量和耗时；模型调用、token 与费用仅在调用方 Agent 提供可靠数据时展示。
- 基础性能指标、单位、样本数、实际负载、阈值及通过情况，区分 HTTP 错误和数据检查失败。
- 压测失败样本是有界采样，明确采样数量；不宣称保留了每个压测请求的完整响应。

报告结论以实际执行结果为依据。首版应提供可供 Agent/CI 消费的结构化结果和供人阅读的报告；具体文件格式、导出及分享方式在方案阶段确定。

报告默认由执行核心在运行结束时生成，不依赖用户额外导出或 LLM 在线；MCP/CLI 返回报告引用，Skill 自动等待并呈现。LLM 可追加解释性分析，但解释失败不能阻止事实报告交付。

## 8. 分期与待确认事项

### 8.1 首个正式交付：完整功能链路与基础并发压测

当前交付：HTTP/REST + JSON、OpenAPI/Swagger 与补充说明、可选宿主源码结论、目标环境、自动接入、LLM 业务理解与链路/数据规划、含业务理解的正式计划、对话/CLI 人工审核、分支/轮询/身份/状态检查、功能及压测执行、自动报告，以及单独重新审核的补充计划执行。MCP Server、CLI 和 Skill 均已提供。计划前探测等原设计附带项的现状见实施记录。

通过 CLI/MCP 发起和检查任务，正式计划经人工审核后在项目策略和审核范围内自动执行；预期以明确需求和接口约定为依据。

仓库提供永久保留的真实 HTTP 测试后端、接口文档、源码及业务约定。首条功能链路包含鉴权、创建、查询和数据断言、失败后的删除与确认清理；另一个独立场景完成基础并发读取和阈值检查，两者共用平台计划与报告。

测试后端支持正常、数据错误和延迟注入模式。Agent 依据文档与源码生成业务理解和计划，人工审核通过后执行；已有且审核有效的版本脱离 Agent 后可通过 CLI/CI 重跑。该交付包含正式执行器、接口与回归测试，不创建随后丢弃的 PoC 工程。

首条链路接通后，在同一 M1 内使用第二个流程结构不同的永久后端，覆盖状态约束、异步等待及身份权限，验证只替换资料、环境和配置即可接入。用户实际后端在资料提供后接入；两种样例通过不等于证明所有后端均可覆盖。

### 8.2 后续扩展候选

多仓库与跨服务链路、多协议、多环境回归、定时任务、多人协作、大规模并行、历史趋势、专用 CI 集成和其他可观察数据接入。是否需要这些能力应由真实使用决定。

### 8.3 正在确认

已完成产品形态、引擎复用、CI 目标和首个交付边界确认。具体接口、数据格式、执行策略和任务顺序见技术方案。

### 8.5 确认记录

- 第 1 轮：资料包含 API 文档与后端源码仓库链接；计划前仅只读探测；新增测试必须形成新版本计划。
- 第 2 轮：CLI/MCP 为主；明确需求与接口约定优先；写操作在项目配置范围内自动执行并记录数据与清理。
- 第 3 轮：Codex/Claude 负责思考，平台提供 MCP 分析与执行工具，CI 执行已有计划；首版为 HTTP/REST + JSON、OpenAPI/Swagger 和补充说明。
- 第 4 轮：采用 MCP + CLI + Skill；功能执行层复用 Hurl；CI 直接访问已部署测试环境；首条正式交付承担完整集成验收，不单独做 PoC。
- 第 5 轮：常规流程、数据断言及基础并发压测均纳入首个交付。技术方案为压测增加 k6 适配器。
- 第 6 轮：项目命名 horus；平台完全业务无关，LLM 基于接口文档与项目源码理解业务，业务理解写入测试计划，供人工审核后执行；MCP Server、CLI 和 Skill 均必需，MCP 可复用成熟开源框架。本轮人工审核要求更新此前“正式计划在配置范围内直接执行”的流程。
- 第 7 轮：接受第一性原理审查的闭环调整，重点验收自动接入、可执行业务理解、当前对话确认、批准后自动收尾报告、两种后端通用性；补充测试单独送审。本轮明确统一 Python 3.12 和 uv，替代此前 Python >=3.12 / CI 3.13 的默认方案。
- 第 8 轮：明确 Codex / Claude Code 等宿主 Agent 接入 horus MCP 是主要场景；从空工作区接入到报告须经 MCP 完整闭环，CLI 不作为正常流程的补缺步骤。分别验收真实客户端、Skill 发现、版本确认、长任务、重试和重连。
- 第 9 轮：用户确认 MCP 实操引导、业务与调用链理解、功能及基础并发测试的核心用途已满足，要求按现有能力收尾并更新文档，不继续增加功能或验收场景。已知实现差异保留为当前限制。
