# horus

<img src="docs/assets/horus-logo.png" alt="horus 标识" width="100%" />

[English](README.md) · [安装与使用](docs/usage.md) · [路线图](docs/roadmap.md)

**在熟悉的编程工具中，从用户视角验证服务。**

horus 是面向所有人的轻量 AI 原生接口测试工作台。描述用户的目标和预期结果，编程助手会结合
接口文档、业务需求和可选的源码信息拟定测试计划。经人工审核确认后，horus 会执行功能测试和基础负载
测试，清理测试数据，并生成测试报告。

测试目标、预期行为、范围和执行限制由你决定。你可以用自然语言提出需求，再按需要查看和调整
计划细节。horus 希望提供专业的测试能力，让测试流程可自动化、可审核，也便于灵活调整。

- **轻量。** 复用已有的编程助手和模型，无需单独部署大型测试平台。
- **本地运行。** 从本机发起测试，计划、执行记录和报告保存在自己的工作区。
- **通用接入。** 可接入支持本地 MCP 的编程工具，在熟悉的环境中使用。

```text
描述用户目标并提供文档 → 审核场景与限制 → 执行测试 → 清理与证据
```

## 功能

- **测试设计。** 提供接口文档链接或本地文件，编程助手结合业务需求和可选的源码信息梳理
  接口调用及依赖，提出测试方案、设计依据和待确认的问题。
- **业务流程验证。** 串联登录、数据创建、状态流转和异步结果，验证访问控制、响应数据与
  业务规则，并将数据准备和清理纳入测试计划。
- **负载测试与响应校验。** 确定并发数和负载范围后，检查请求完成情况、响应时间、HTTP 错误
  以及数据正确性。
- **测试报告与执行记录。** 查看业务验证结果、失败项和性能指标。业务流程图说明测试范围，
  详细检查及请求响应记录用于问题排查。
- **重复执行与回归测试。** 每轮计划与结果保存在独立目录中。已确认的计划可在原范围内重复
  执行，历史记录便于对照。

目前为 alpha 版本，被测服务的编程语言不限，
接口范围为 HTTP/REST + JSON。具体限制见
[架构说明](docs/architecture.md#current-limits)。

## 快速开始

把下面这段话发给你的编程助手：

```text
请按照 https://github.com/xucailiang/horus/blob/master/docs/usage.md 安装 horus，
在当前编程工具中完成接入，并验证连接。
```

编程助手可以完成安装和配置。手动安装及其他工具的接入方式见[使用指南](docs/usage.md)。
Codex 和 Claude Code 已完成验证，其他 MCP 客户端使用同一套测试流程。

然后给它接口文档和测试目标：

```text
用 horus 测试这个服务：<服务地址>，导入接口文档：<在线链接或本地文件路径>。
梳理业务调用关系，设计一轮功能测试和基础并发测试。
围绕用户要完成的目标、预期结果和相关失败路径来设计。
先把要验证的业务、通过标准和负载范围直接给我看，等我确认后再执行。
最后清理本轮数据，给我一份能看懂业务结果、失败原因和关键指标的报告。
```

计划直接在对话中展示，确认后才保存和执行。计划或负载有变化时，由你重新确认。

## 测试报告

报告摘要包含测试范围、通过项、失败项、性能表现和数据清理状态。业务流程图将结果与已确认的
计划对应起来，未执行的检查和未解决的清理问题会单独列出。

每轮计划与结果保存在同一目录，文档使用当前对话的语言：

| 文件 | 内容 |
| --- | --- |
| `plan.md` | 确认要测的业务、预期结果、范围和业务流程图 |
| `report.md` | 业务结果、问题、关键指标和业务简图 |
| `details.md` | 排查问题时需要的详细检查和请求响应记录 |

## 发展方向

horus 希望降低专业测试的使用门槛，让用户始终掌握测试目标和执行细节。
[路线图](docs/roadmap.md)关注如何将用户目标转化为测试设计、自动执行更复杂的场景，以及在
服务迭代中复用和维护测试。项目优先关注开源用户的实际使用需求与长期可维护性。
